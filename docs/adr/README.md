# 架构决策记录（ADR）

这里记录「为什么这么做」——尤其是那些只看代码看不出来、改起来又会踩回的取舍。
代码回答「是什么」，SPEC 回答「对外契约是什么」，ADR 回答「当时为什么选它」。

## 什么时候写

满足任意一条就值得写：

- 改动跨了多个模块，且后续很容易被「顺手改回去」；
- 有两个以上都说得通的方案，最终靠某个具体故障或实测数字做了选择；
- 定下了一条不变量（顺序、边界、默认值），破坏它不会让测试立刻变红；
- 明确决定「不做什么」，且这个决定需要向后来者解释。

不值得写的：改个函数名、加一个参数、纯 bug 修复。

## 格式

每条 ADR 至少包含：

1. **状态**：提议 / 已采纳 / 已废弃 / 被 000X 取代
2. **背景**：当时的问题与约束，带上实测数字或故障现象
3. **决策**：选了什么，边界规则是什么
4. **被否方案**：为什么没选，越具体越好
5. **后果**：收益、代价、已知未达成的部分
6. **验证**：怎么证明这次改动没有改变行为

文件名用 `NNNN-短横线标题.md`，编号只增不减；被取代时保留原文，只改状态并链接到新条目。
