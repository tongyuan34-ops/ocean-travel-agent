# 上下文成本治理：如何让一句「你好」从 16,233 token 降到 1,875

> 一个旅行规划 Agent 的真实重构记录：工具描述膨胀、按轮工具绑定、插件式技能与 MCP 双向接入。
> 本文只讲一个问题——**每一轮请求都要重发的那部分上下文，该怎么管**。

---

## 一、问题的形状：不是「工具太多」，是「每轮都全发」

大多数关于 Agent 成本的讨论集中在两件事：历史太长要摘要、输出太长要截断。
但还有一块更隐蔽的开销：**工具定义**。

对话历史会滚动，可以被摘要折叠；`bind_tools` 的产物不会。它是每一轮请求里
原样重发的一份 JSON Schema。你加一个工具、给参数多写两句说明，成本就按
「轮数 × 工具数 × 描述长度」线性叠加。

重构前的实测（`tiktoken`，cl100k）：

| 项 | 重构前 | 重构后 |
|---|---|---|
| 系统提示词 | 3,089 | 1,554 |
| 工具 schema | **13,144**（32 个全量） | 321（仅常驻元工具） |
| 一句「你好」的固定输入 | **16,233** | **1,875** |

用户只说了一句「你好」，先付了 16,233 token，其中 81% 是工具定义。
更糟的是首字延迟——这些 token 在模型开口之前就要处理完。

而那份 `aggregate_sheet` 的参数说明，对一个问好的人没有任何价值。

**这就是「上下文成本治理」要解决的问题：不是把功能砍掉，而是让每一轮只带
这一轮用得上的东西。**

---

## 二、方案一：按轮工具绑定（不是砍工具，是改「什么时候给」）

### 2.1 分组：按能力域而不是按模块

32 个业务工具被分成 8 组，顺序即优先级：

| 组 | 能力域 | 代表工具 |
|---|---|---|
| `trip` | 行程规划 | `plan_trip` / `get_weather` / `plan_route` |
| `stay` | 住宿与交通 | `recommend_stay` / `recommend_transport` |
| `delivery` | 行程交付 | `export_trip_pdf` / `render_trip_map` |
| `docs` | 文档与表格 | `read_document` / `query_sheet` / `aggregate_sheet` |
| `file` | 本机文件 | `read_file` / `write_file` |
| `web` | 公开网页检索 | `search_web` / `fetch_url` |
| `social` | 社媒内容采集 | `search_social_session` |
| `media` | 图片生成 | `generate_image` |

每轮按用户这句话的触发词只绑命中的组：

```
「你好」                  → 0 组，只留元工具
「帮我规划三亚2天」        → trip
「那第二天呢」             → trip（沿用上一轮）
「把这个表按金额排一下」    → docs
```

### 2.2 路由不用 LLM，用关键词 + 正则

这是整篇文章里最容易被质疑的决定。用 LLM 做意图分类看起来更准，但：

- 它多花一次模型调用，而且是在**首 token 之前**多花——延迟和成本都更差；
- 同一句话两次分类结果可能不同，判断不稳定；
- 关键词是纯 CPU、微秒级，而且能被单测完全钉住。

中文不需要分词，子串匹配就够用；带数字的形态（「4 天」「第二天」）单独写正则，
否则「4 天」会退化成匹配单字「天」，误伤「今天」。

### 2.3 猜错了怎么办：三层兜底

关键词一定会漏。所以这个方案不是「一次判断定生死」，而是三层护栏：

1. **宁可多绑一组。** 多绑一组约 300–900 token，比「模型想调却没工具」便宜得多；
2. **本轮一个信号都没命中时，沿用上一轮的组。** 「那第二天呢」这种纯追问不会掉工具；
3. **模型可以自救。** 常驻元工具 `discover_tools` 让它说明意图，命中的组会被激活到
   会话，下一轮自动可用。

第三条也是 `discover_tools` 必须常驻的原因：没有它，关键词漏网时模型只能回答
「我做不到」。另外附件类型是强信号——传了 `.xlsx` 却只说「看看」，按扩展名直接补
`docs` 组，权重高于单个关键词。

### 2.4 两个实现上的坑

**图要按工具集合缓存。** `bind_tools` 是在构图时固定的，不同轮次的工具子集不同，
所以缓存的键是 `{工具名集合: 图}`，不是「一张图」。上限 4 张，避免组合爆炸。

**上限存在的意义不是省 token，而是不要退化成全量。** 一轮最多绑 16 个工具；
全命中时如果 32 个全给回去，这层就白做了。

逃生舱：`TOOL_ROUTING=all` 可以整体关掉路由，退回全量绑定，专用于排查
「模型说没有这个工具」这类问题。

## 三、方案二：插件式技能——清单进提示词，正文按需加载

技能系统的诱人做法是把技能说明全塞进系统提示词。四个技能的完整步骤合起来
上千 token，**每轮都塞进去，和全量绑工具是同一个错误**。

所以真正进每轮提示词的，只有一份「清单」：

- 每个技能一行：名字 + 一句话描述；
- 四个技能合计约 **230 token**；
- 步骤正文只在两种情况下进上下文：用户显式选中（`/skill`、选择器、会话配置），
  或模型自己调用 `use_skill` 取。

配套三条约束：

| 约束 | 数值 | 作用 |
|---|---|---|
| 技能描述长度 | ≤ 160 字符 | 保证「一行一个」不变成段落 |
| 步骤正文 | ≤ 6,000 字符 | 防止单个技能吃光上下文预算 |
| 单轮技能工具数 | ≤ 4 | 技能工具只在命中时绑，且总量封顶 |

技能的代码也有成本维度上的取舍：`tools.py` 用进程内 `importlib` 加载，不起子进程。
不起子进程不是为了省 token，而是因为起子进程会绕过权限确认、污点拦截、调用预算与
重试——**这些机制本身就是成本闸门**。同理，技能目录随版本分发、不做远程下载：
装技能等于装可执行代码，这个口子不能用「方便」换。

还有一个容易被忽略的细节：纯提示词技能的模板会内联进上下文，但总量封顶
1,500 字符，长模板只留路径，交给技能代码自己读。否则「模板」会变成第二个
工具描述膨胀源。

## 四、方案三：MCP 双向接入的成本边界

MCP 解决的是「工具从哪来」，但它同样会推高每轮固定开销——外部服务端的工具
最后还是要变成 JSON Schema 发进上下文。所以接入必须带边界。

**服务端方向**：34 个工具里只暴露只读的 17 个。写文件、删文件、换壁纸不暴露，
原因不是安全策略，而是架构事实：应用内的写操作依赖 `PermissionBroker`，它把确认
请求推给前端 SSE，等用户点「允许」；**MCP 场景里没有那个前端**，`require_permission`
找不到裁决通道就一律拒绝。把这些工具挂上去，客户端会看到一堆工具，调了必然
`PERMISSION_DENIED`——「能列出但永远失败」比「不列出」更糟，客户端会反复重试，
用户看到的是这个服务坏了。

**客户端方向**：外部 MCP 服务端的工具进入同一个工具池，走同样的路由、预算与权限。
否则「接了三个 MCP 服务」就会变成「每轮多付三份 schema」。

**协议层自己写**：官方 Python SDK 会带进 anyio / httpx / sse-starlette 一整套，
而协议本体只是 JSON-RPC 2.0 + 换行分帧 + 五六个方法，约 200 行。依赖树收紧的收益
不只是安装体积，还有启动时间和打包体积——这在桌面版上是能感知的。

## 五、量化收益：省下来的钱，没有拿质量去换

| 指标 | 重构前 | 重构后 | 变化 |
|---|---|---|---|
| 工具 schema | 13,144 | 321 | **−97.6%** |
| 一句「你好」固定输入 | 16,233 | 1,875 | **−88.4%** |
| 系统提示词 | 3,089 | 1,554 | −49.7% |
| 后续版本再压 | 11,319 | 1,829 | −84% |
| 工具召回率 | 73.3% | 88.3% | **+15.0 pp** |
| 评测通过率 | 72.5% | 82.9% | **+10.4 pp** |

（schema 与「你好」的数字来自同一次重构的同口径测量；最后一行是后续继续精简
提示词后的版本，口径不同，不要跨行相加。评测为 41 条真实模型用例。）

质量没有掉，原因不复杂：**召回率的瓶颈从来不是「工具给得不够多」，而是
「工具描述有歧义」**。路由去掉的是噪声，不是能力。误调数比通过率更值得盯——
一次误调基本等于某条工具描述写得让人分不清该用谁。

真实单轮对话的账单侧数据：8.5k–13.3k token，约 ¥0.022–0.034。
技能清单的 230 token 在这个量级里几乎可以忽略——这正是「清单 + 按需加载」
想要的结果。

## 六、失败尝试：比成功方案更值得写

### 6.1 删掉「事实必须先调工具」，模型一个工具都不调

精简提示词时删掉了这条规则，理由是「工具描述里已经写了怎么用」。
端到端一测，模型凭常识直接排出了一份看起来很完整的行程，6 个工具一个都没调。

结论：**工具描述管「怎么调」，提示词管「什么时候必须调」，两者不能互相替代。**

### 6.2 用 LLM 做意图分类

被否决。多一次调用、发生在首 token 之前、结果不稳定——三个缺点都直接打在
体验上。关键词方案会漏，但漏了有三层兜底；LLM 方案错了你甚至不知道它为什么错。

### 6.3 每轮自动检索知识库

看起来更「智能」，实际有两个代价：每轮固定多花几百 token；检索不准时会污染
这一轮的全部回答——用户问「你好」也带上三条行程规则，模型反而容易跑题。
最终做成工具，让模型自己判断要不要查，调用过程在 SSE 里可见，出问题能复盘。

### 6.4 把技能做成远程下载

被否决。装技能等于装可执行代码，和 MCP 的信任边界是同一件事。技能目录随版本
分发，版本一致性和安全边界都能保证。

### 6.5 把写工具暴露给 MCP 客户端

被否决，理由见第四节。这条的价值在于**它看起来是个功能缺失，实际是正确行为**。

### 6.6 不按工具集缓存图

踩过的坑。`bind_tools` 在构图时固定，缓存一张图会让不同工具子集的轮次复用到
错误的图——表现是「模型有时能看到某个工具，有时看不到」，极难排查。

### 6.7 一次归因实验：解绑工具并不能改人格

这是唯一一个「方向猜错但收获很大」的尝试。现象是用户说「你能不能变成知心大姐姐」，
语气变了但结构仍是行程规划。我以为 22 个工具 schema 每轮都在暗示「你是旅行 agent」，
于是写脚本做单变量对照，每臂 3 次：

| 变量 | 带旅行词 |
|---|---|
| 原样（14 条规则 + 22 工具） | 3/3 |
| 只解绑 22 个工具 | 3/3 |
| 只改身份那一句 | **0/3** |

解绑工具对人格没有影响，真正起作用的是提示词第一句。「工具在上下文里的暗示作用」
被高估了——这对成本治理是个好消息：**路由工具不会改变 Agent 的身份感**，
可以放心做。

## 七、五条可以搬走的判断标准

1. **先分清「固定开销」和「滚动开销」。** 历史可以摘要，工具 schema 不能；
   优化要打在固定开销上。
2. **适用于所有工具的规则留在提示词，只适用于某一个的搬进它的描述。**
   同一句话写两遍的代价不只是双倍 token，还有两处迟早不一致。
3. **显式指令直接注入，自主发现只给清单。** 「用户已经选了」和「模型可能要选」
   是两种确定性，不该付一样的钱。
4. **任何裁剪都必须有兜底。** 多绑一组、沿用上一轮、元工具自救——没有兜底的
   路由会把「省 token」变成「功能时灵时不灵」。
5. **每个优化都要能用数字钉住。** 用单测断言「一句闲聊的固定输入不超过 N token」，
   否则下一次加工具时，膨胀会静悄悄地回来。

---

## 结语

这套东西的价值不在于「省了 88% 的 token」，而在于把一件模糊的事变成了可测量的
工程约束：**每轮请求都是一次预算分配，你要说清楚这一轮为什么带这些东西。**

工具会越来越多，技能会越来越多，MCP 服务也会越来越多。唯一不会变的是
「每轮只带用得上的」这条原则。
