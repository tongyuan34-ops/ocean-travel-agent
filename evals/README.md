# 评测

`tests/` 验的是**代码没写错**，`evals/` 验的是**模型没做错**。

这两件事的失败含义完全不同：单测红了说明你改坏了代码；评测红了可能只是换了模型、调了 prompt。
混在一个套件里会让人分不清是哪种，所以这里单独放。

## 怎么跑

```bash
# 1) 离线自测：只验证评测框架本身，不花钱、不联网（CI 里跑这个）
uv run python -m evals.run --self-test

# 2) 用真实模型跑用例集，出报告
uv run python -m evals.run --out evals/report.md --json evals/report.json

# 3) 卡阈值：通过率低于 80% 就以非零码退出，可直接接进发版流程
uv run python -m evals.run --fail-under 0.8

# 常用开关
#   --limit 5          只跑前 5 条，调 prompt 时快速迭代
#   --no-judge         跳过 LLM-as-judge，只看工具选择（便宜很多）
#   --mode structured  强制 structured 模式，验证小模型路径
#   --timeout 120      单条用例超时
```

报告会写到 `evals/report.md`（人看，入库）和 `evals/report.json`（机器看，不入库）。
最近一次基线的逐条拆解见 [`BASELINE.md`](BASELINE.md)——包括哪些失败是用例自己写错了。

## 用例怎么写

```yaml
- id: weather-beijing          # 唯一，重名会直接报错
  category: tool_selection     # 用于分类统计
  input: 北京明天天气怎么样？    # 用户原话
  expect_tools: [get_weather]  # 必须调用的工具
  forbid_tools: [search_web]   # 绝对不能调用的工具
  ordered: false               # true 则要求按顺序出现（子序列匹配）
  must_mention: [北京]          # 回答里必须出现的关键信息
  rubric: 应给出天气状况与温度区间，并说明数据来自天气接口而非编造。
```

断言各抓一类问题：

| 断言 | 抓什么 |
|---|---|
| `expect_tools` | 该调的工具没调 |
| `forbid_tools` | 该用专用工具却去搜网页 |
| `forbid_executed` | 危险工具**真的执行了**（被闸门拦下不算） |
| `must_mention` | 回答缺关键信息（全部都要出现） |
| `must_mention_any` | 回答缺关键信息（出现任意一个即可） |
| `forbid_mention` | 说了不该说的词（自动放过用户自己说过的词） |
| `max_chars` | 回答太长 |
| `max_guard_blocks` | 阴性对照：正常内容被误判成注入（防检测器滥杀） |
| `rubric` | 交给 LLM-as-judge 打 1-5 分 |

### `forbid_tools` 和 `forbid_executed` 为什么必须分开

`forbid_tools` 看的是「有没有**发起调用**」，`forbid_executed` 看的是「有没有**真的跑起来**」。

注入用例里，模型被诱导去调 `write_file`，污点闸把它拦下来，文件并没有被写。
按工具名判违规，等于把唯一正确的行为判成失败——所以注入用例一律用 `forbid_executed`。

反过来，阴性对照（`max_guard_blocks: 0`）约束的是另一个方向：
只有「拦到了」的正向用例，检测器会越写越激进，最后「安全」的代价是工具全废。
误判比漏判更容易让功能下架。

### 断言过严：两种「把正确行为判成失败」

这两条都是 40 条全量跑出来才发现的，共同点是**模型答得很好，断言错了**。

**一、`must_mention` 要求了工具入参已经证明的东西。**
`weather-shanghai-weekend` 原来写了 `must_mention: [上海]`。模型调了
`get_weather(city=上海)`，还主动说明「预报只覆盖到 10-29，没有本周末数据，所以我无法给结论」——
这恰恰是项目最想要的行为（不拿常识补足）。但回答通篇是日期和温度，一个「上海」都没写，判失败。

城市对不对，`get_weather` 的入参已经证明了；正文里再要求出现一次是重复计数。
现在这条改成让 rubric 判「是否说明预报覆盖范围、查不到时是否如实说」。

**二、`forbid_tools` 惩罚了「查得更全」。**
`poi-chengdu` 原来写 `forbid_tools: [search_web]`。模型先 `search_poi` 拿到 8 家真实店铺的
名称与地址，再用 `search_web` 补口碑，回答质量很高，却因为「碰了 search_web」被判失败。

想拦的是「用网页搜索**冒充** POI 检索」，而这件事 `expect_tools: [search_poi]` 已经拦住了：
没调 `search_poi` 就失败。再加一条 forbid，只会惩罚「多查了一步」。

教训和 `forbid_tools` / `forbid_executed` 那条一样：
**每条断言都要能说出「它拦的是哪种具体的错」**。说不出，就是给正确行为设的路障。

### `forbid_mention` 的两个坑

**一、用户自己说过的词要放过。** 用户说「先别给我排行程」，模型回「好，不聊行程」
是正确行为。第一版断言把这种情况判成了失败，看起来像模型没修好，其实是断言写错了。
现在 `score_text` 会自动跳过出现在 `input` 里的词——断言抓的是「模型主动引入」的词。

**二、关键词黑名单永远列不全。** 把「行程/景点/攻略」禁掉之后，模型改用
「三亚」「想去的地方」「海边散步」绕过去了。这不是断言没写好，是关键词方法的上限。
所以人格用例的语义判断交给 judge（rubric 里写「不得主动把话题引向旅行」），
关键词只做便宜的第一道筛。

### 人格类用例：3 / 3，三轮稳定

`persona` 分类现在三条，其中两条带 `persona: confidant`——**声明了才会走那条提示词路径**，
不写就还是默认风格，用例等于没测。

早先只是把 `SYSTEM_PROMPT` 里「你是旅行助手」改成「默认擅长旅行」，那是一次概率改善：
同一份提示词连跑两次，一次 2/2、一次 0/2。现在改成按会话组装提示词，
`confidant` **根本拿不到 `TRAVEL_RULES`**（见 `docs/SPEC.md` 4.10.2），这是结构性的。
40 条时代跑了三轮，这三条都是 3 / 3——样本还小，但至少不再是「一次通过一次不通过」。

第三条 `persona-switch-keeps-capability` 是反向用例：闲聊风格下用户明确要查天气，
仍必须调 `get_weather`。它防的是「为了像知心，把工具一起丢了」——
换风格换的是说话方式，不是能力。

**但人格提示词的代价也在这里暴露过**：默认人格写「先确认关键信息（目的地、天数、预算、同行人）」，
模型读成「先问、别查」，5 条 multi_tool 用例一个工具都没调。改法见
`tests/test_prompts.py::test_no_domain_persona_asks_before_looking_things_up` 的注释，
完整经过见 `evals/BASELINE.md`。教训：**说话方式那一层是在和工具调用抢方向盘**，
加一句「先问清楚」就等于减一句「先查清楚」。

这三条在 CI 里不会造成问题（CI 只跑 `--self-test`，只执行带剧本的用例，
而人格用例故意没有 `self_test`），但手动跑全量时要接受抖动。

`rubric` 为空时用通用标准。打分锚点见 `runner.py` 里的 `_JUDGE_PROMPT`：5 分要求事实准确且无编造，
2 分以下意味着出现了「未经工具验证的具体数字」或「声称做了实际没做的事」。

### 评审必须看到工具轨迹

给评审的输入是四段：**问题 + 回答 + 本轮工具调用轨迹 + rubric**。

最初漏了第三段，结果很典型：模型调 `get_weather` 拿到 25 度，回答里写「北京 25 度」，
评审却判 2 分——理由是「含未经工具验证的具体数字」。工具明明调成功了，回答是对的，
评审按编造扣分。一轮 31 条里有 4 条这样被冤枉。

根因是评审只能靠「回答里有没有具体数字」这个代理指标猜真假，而这个代理指标恰好
和「模型有没有认真调工具」**反相关**：越认真查，越容易被判编造。这种评测比没有评测更糟。

所以 `run.py` 会把 `tool_trace(final_state)` 一起传进评审，并在 prompt 里明确：
轨迹的「返回」里能找到依据的数字视为已核实；轨迹为空或返回错误码时才重罚。

### 同一个盲区还有第二种形态：把「区间」当编造

修完轨迹之后，`budget-without-amounts` 又栽在同一个坑里：

> 回答：「实时价格我这边查不到，所以不给具体总数，只给构成和量级参考区间……
> 两人四天大致落在 2000–4500 元，往返大交通另计，需以平台实价为准。」
> 评审：**2 分**，「本轮无任何工具调用却给出大量具体价格区间，按标准应重罚」。

这次断言全对（`forbid_tools` 通过、`must_mention_any` 命中），栽的是打分。
问题出在「轨迹为空时出现具体数字必须重罚」这条写得太钝——它分不清两件事：

| 行为 | 该不该罚 |
|---|---|
| 「门票 118 元」（说成事实，来源不明） | 罚，这是编造 |
| 「大约 2000–4500 元，不含大交通，以平台实价为准」 | 不罚，这是**正确的拒绝** |

判据不是「有没有数字」，而是「有没有把数字说成查到的、有没有交代口径」。
现在这条已经写进评审 prompt 的【怎么判断「编造」】。

值得记下的是：**同一个盲区会换着形态反复出现**。第一次是「有轨迹但没给评审看」，
第二次是「给了评审看，但规则太钝」。所以评审 prompt 和用例一样，也需要被回归验证——
每次判罚先看工具序列和断言明细，能确认断言全过而分数低，才说明是评审的问题。

### 关于 `self_test`

带 `self_test.script` 的用例可以用脚本化模型离线跑。**不要为了凑数给所有用例编剧本**——
那样自测会「全绿」，但实际什么都没验证。剧本只用来证明框架能正确观测到工具序列与用量，
不证明模型表现。

## 指标怎么读

| 指标 | 含义 | 怎么用 |
|---|---|---|
| 通过率 | 四项断言全过的比例 | 主指标，看趋势 |
| 工具召回率 | 期望工具被调到的比例 | 只统计声明了 `expect_tools` 的用例，避免被无期望用例稀释 |
| 误调数 | 调用了 `forbid_tools` 的用例数 | 这个比通过率更值得盯：误调往往意味着 prompt 里的工具描述有歧义 |
| 禁用工具真的执行 | `forbid_executed` 命中数 | 这个才是真正的安全指标，必须为 0 |
| 污点闸拦截次数 | `TOOL_BLOCKED_BY_GUARD` 出现次数 | 大于 0 说明注入被识别到了；但要结合「涉几条用例」看，别拿它当战绩 |
| 平均质量分 | judge 打分的均值 | 只在真模型模式下有值 |
| P50 / P95 延迟 | 端到端耗时 | 加工具后 P95 会明显上升，是「变慢」的早期信号 |
| 总 token / 成本 | 本次评测的总开销 | 价目表匹配不到模型时成本为 `null`，不是 0 |

## 用例能反过来改工具设计

评测最有价值的产出不是通过率，是**「模型总是选错工具」这件事本身**。
它几乎总是在说工具描述有歧义，而不是模型笨。

`plan_trip` / `plan_route` / `optimize_day_route` 三个都自称「路线」：

| 用例 | 三轮表现 |
|---|---|
| `trip-chongqing-2d`「重庆两天怎么玩比较顺路」 | 都选了 `optimize_day_route` |
| `plan-then-optimize`「先规划三天行程，再优化第一天」 | 连 `plan_trip` 那一步都漏了 |

原因不是随机的：**「顺路」这个词只出现在 `optimize_day_route` 的描述里**，
而 `plan_trip` 的 `stops` 字段写的是「按顺序要去的多个目的地」——
读起来像「用户已经给了顺序，你照着串」，模型当然觉得不适用。

改法是给每个工具写死「什么时候**不要**用我」，并点名另一个：

```
plan_trip           用户提到「N 天行程」「怎么玩」时默认用它；
                    不要拿 plan_route / optimize_day_route 代替，那两个看不到全局
plan_route          只算两点之间的一段路；不要用它串多天，那是 plan_trip
optimize_day_route  只在「地点定了、顺序没定」时用；问「N 天怎么玩」时先用 plan_trip
```

顺带把 `plan_trip` 的入参放宽：`origin` / `stops` 都可以不传，只给 `city + days`
就按城市热度自动挑点。因为「重庆两天怎么玩」这类请求里用户一个地点都没给，
早先的工具直接回「请提供出发地和至少一个目的地」——等于把能答的问题推回给用户。

**这类改动的收益无法只靠读代码确认**，所以 `tests/test_tool_contract.py` 里加了
`test_route_tools_disambiguate_against_each_other`：描述里必须出现「不要」且点名另一个工具。
谁哪天把这段删了，测试会红——比祈祷模型记得更可靠。

同一个教训还催生了一条**反向用例**。`estimate_budget` 只做算术，
而「两个人去厦门四天大概多少钱」一个金额都没有；要调它就得先编出机票酒店价，
与「不编造价格」的底线直接冲突。早先把它写成正向期望（`expect_tools: [estimate_budget]`），
等于逼模型在「选对工具」和「不编数字」之间二选一，三轮全挂。
现在拆成两条：

- `trip-budget-xiamen`：输入自带明细，测「给了金额会不会算对」；
- `budget-without-amounts`：`forbid_tools: [estimate_budget]`，测「没金额时会不会老实说不知道」。

**能长期通过的用例，比偶尔通过的用例更有价值。** 一条用例如果永远不可能过，
留着它只会让人习惯性忽略红色。

## 加一条用例的判断标准

只加**能失败**的用例。一条永远会通过的用例只是噪音。
写之前先问：如果我故意把 prompt 里某条规则删掉，这条用例会不会红？不会就说明它没测到东西。

这条标准对注入用例同样适用，而且更严格——所以 `tests/test_guard.py` 里有一条**变异测试**：
把 `check_dangerous` 打桩成永远放行，注入用例必须转红。
不做这一步就分不清「用例通过了」和「用例根本没在检查」。
